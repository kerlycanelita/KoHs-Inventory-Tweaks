# 1.3.0 research: the inventory of Minecraft 26.2, Super Fast Inventory and ping

October 2026. The question from the owner: fix the inventory bugs and rough edges
players hit in 26.2, find out whether Super Fast Inventory really changes anything
on servers at 69 to 199 ms of ping, and make the inventory feel as good as it can
without crossing what a Vanilla client could do. The research looked at players in
general, not at one setup.

## Sources

- Mojang's tracker, read through the frontend's own search endpoint
  (`POST https://bugs.mojang.com/api/jql-search-post`, JQL `text ~ "..."`): about
  1,600 open issues about inventories, containers, keys and the mouse, filtered by
  hand for 26.x.
- Modrinth's mod listings for 26.2: what players install to fix the inventory
  (`cursorcentered-fix`, `totem_optimizer`, `keystroke-gui-exit`, `better-screens`,
  `mouse-tweaks`, `smooth-gui` and others) and what their pages say about ping and
  flicker.
- The 26.2, 26.1.x and 1.21.11 client jars, read with `javap`, to confirm each bug
  in the code before fixing it and to find where each fix belongs.
- Grim Anticheat 2.3.74 (open source): how it models the client's inventory, to
  check that nothing in 1.3.0 can look wrong to it.

## Super Fast Inventory at 69 to 199 ms

`sfi-value` lab, 26.2, singleplayer (network latency adds the same to both sides,
so it is left out): each trial presses the inventory key, then flicks to a totem
and presses F a set time later, as one practised motion.

| Delay after the key | Vanilla: totem reached | Super Fast Inventory | Click leaves (p50), Vanilla / Super Fast |
| ---: | ---: | ---: | --- |
| 0 ms | 0/10 | 10/10 | — / 33.7 ms |
| 10 ms | 4/10 | 10/10 | 26.7 / 33.9 ms |
| 20 ms | 4/10 | 10/10 | 35.3 / 35.1 ms |
| 30 ms | 7/10 | 10/10 | 43.4 / 42.6 ms |
| 40 ms | 7/10 | 10/10 | 51.5 / 50.8 ms |
| 60 ms | 10/10 | 10/10 | 76.4 / 75.9 ms |
| 90 ms | 10/10 | 10/10 | 101.7 / 101.4 ms |

The screen appears 4.1 ms after the key (median, at most 8 ms) instead of 21 to 31 ms
(at most 47 ms). The click of a fast hand is rescued instead of lost, and it leaves
at the moment a Vanilla client first could. That is all Super Fast Inventory can do:
it cannot shorten the trip to the server, and it must not try (see the ban of
2026-10-07 in the 1.2.1 notes).

## What players feel at ping: the flicker

On the server, `handleContainerClick` always applies a click; when the click's
state number is old, it answers with the whole inventory (`broadcastFullState`).
Every inventory change on the server moves the state number on, and in a fight
armor loses durability on every hit, so at 70 ms and more almost every click is
answered with a full inventory. When a second click follows within the ping, the
answer to the first arrives after the second is already shown, and Vanilla puts
it on screen: the second slot jumps back until its own answer arrives. That is
the "ghost totem" flicker players blame on ping.

The ping lab (`KoHs-Debug-Tools/inventory-ping-lab/run.py`) plays double
re-totems against a local 26.2 server with Grim 2.3.74, Ping Equalizer adding the
latency and the armor wearing every 100 ms, and counts frame by frame how long a
slot shows anything but the player's own result:

| Added ping | Vanilla: combos that flicker | ms per combo | Steady inventory |
| ---: | ---: | ---: | ---: |
| 0 ms | 0/24 | 0 | 0/24 |
| 70 ms | 4/24 | 7.4 | 0/24 |
| 130 ms | 6/24 | 11.6 | 0/24 |
| 200 ms | 11/24 | 27.7 | 0/24 |

Grim raised no alert. (The Timer alerts printed while the client joins come from
the connection itself and appear with any build.)

### Why Steady inventory is safe

- It changes only what a full answer puts on screen while the inventory is open,
  and only on the slots changed by the player's own clicks still on their way.
  Every other slot shows the answer at once; single-slot updates are never held.
- Each click packet it lets the client send is one a Vanilla client sends when the
  answer is still in transit: the same keys, the same slot, the state number the
  client has. The server ignores the predicted slots of a click with an old state
  number and answers it whole, so nothing it acts on differs.
- Grim models the client's inventory from the click type and slot and corrects it
  against the server; it does not check the predicted slots or the state number of
  a click (`CompensatedInventory`, read in 2.3.74). Outside the inventory nothing
  can differ: whatever was kept aside is put on screen the moment the screen
  closes, before the next tick, so items used, placed or held afterwards are what
  a Vanilla client would hold.
- Turning it off returns to Vanilla.

## Leave with movement keys

`keystroke-gui-exit` (121k downloads) shows players want it. It is off by default:
one key doing two things is a choice each player should make. The close packet is
sent before the movement, the order a Vanilla player gets by pressing Escape and W
in the same instant; the `inventory-feel` lab checks that order.

## Not done

- Extra packets to make the server answer sooner (what `totem_optimizer` does):
  anything a Vanilla client could not send is out.
- Moving or dragging items for the player, InventoryMove, clearing a queued attack
  or use: automation or a change in what the server receives.
- Hiding the recipe book by toggling the book itself: that sends a settings packet
  and rewrites the player's saved choice. Hide recipe book only changes what the
  screen shows.

## Checked again on an idle machine

During one run at 200 ms, two of 24 combos played as "close the inventory in the
same gesture" lost their second key: the trace showed the input fence of Super
Fast Inventory still up about 130 ms after the opening, holding that key, and the
lab then closing the screen directly, which drops what the fence holds. The owner
was using the computer during that run. Repeated on 2026-10-19 with the computer
idle and the fence state printed at every key: 32 combos open and 32 closed in the
same gesture, with and without Steady inventory, no key lost, the fence never up
at a key, and the flicker at 200 ms down from 12 of 32 combos to none. The two
losses came from real input reaching the lab's window, not from the mod. A player
closes with a key, which the fence delivers in order.

# Minecraft 26.1.2 input and render audit

Date: 2026-09-06  
Scope: KoHs Inventory Tweaks 1.0.7 for Minecraft 26.1.2  
Priority: low-latency player input without changing Vanilla server semantics

## Invariants

- Opening the player inventory may reduce client-side presentation latency, but it must not synthesize inventory transactions or bypass server validation.
- Closing a container must keep Minecraft's native `LocalPlayer.closeContainer()` path and its single `ServerboundContainerClosePacket`.
- Cursor Landing owns one placement during the synchronous screen-opening transaction. Real mouse movement owns the cursor immediately afterwards.
- Mouse deltas sampled while the pointer controlled the world camera must not become inventory hover or drag input.
- GUI scaling must transform rendering and pointer input exactly once.
- Live visual controls must not synchronously rewrite JSON on every drag sample.

## Questions and findings

### Fast opening and keyboard input

1. Does the fast-open controller run while another screen is open? No; the observation gate rejects any non-null screen.
2. Does it run while an overlay is open? No.
3. Does it scan modded key mappings while the feature is disabled? No.
4. Can slot or offhand input inside an open inventory enter the fast-open decision queue? No.
5. Does a normal inventory press still open during the same input poll? Yes.
6. Does an ambiguous chord remain available to Vanilla? Yes; only an unambiguous inventory input is accelerated.
7. Are queued key presses discarded when acceleration declines? No.
8. Can a pre-open camera delta become a synthetic slot drag? It could before this audit; the inherited delta pair is now cleared immediately after the synchronous open.
9. Is mouse movement from the following input poll retained? Yes.
10. Are any click, swap, slot or transaction packets synthesized? No.

### Cursor Landing

11. Is the requested screen recorded before Minecraft starts opening it? Yes.
12. Is final placement made before the screen layout exists? No; it now occurs when `Minecraft.setScreen` returns.
13. Can another release hook overwrite the final position during the same opening transaction? The final post-transaction placement restores the selected target once.
14. Is the cursor corrected on tick or render? No.
15. Is there a retry window that can drag the cursor after real player movement begins? No.
16. Does a resize count as a new cursor landing? No.
17. Does Centered Mouse affect chests or other containers? No; its target classification remains player-inventory-only.
18. Are saved edge coordinates resolved against the same inclusive pixel range as the preview? Yes; runtime uses `width - 1` and `height - 1`.
19. Does a custom item target resolve through the same GUI transform as a free point? Yes.
20. Does Cursor Landing continuously fight Raw Input or another pointer mod? No; incompatible pointer owners disable Cursor Landing, and a successful landing is one-shot.

### Closing while several keys are held

21. Does Super Fast Inventory participate when the inventory is already open? No.
22. Does `AbstractContainerScreen.keyPressed` close synchronously when the configured inventory key is pressed? Yes.
23. Does holding movement, jump or sprint block that callback? No; GLFW callbacks are processed sequentially.
24. Does closing preserve the native local and network order? Yes: send one Vanilla close packet, then execute the native client-side close.
25. Should the mod send a close packet directly to make the animation look faster? No; it risks duplication and semantic drift without reducing input-poll latency.
26. Could a stalled render frame make the close look late before Minecraft receives the callback? Yes. That is frame latency, not a slow close implementation.
27. Did the focused stress scenario lose any close input? No: 32/32 closures succeeded while four movement-related bindings remained held.
28. What was the observed macro confirmation latency? 27.614-46.920 ms, with a 33.161 ms median; the macro confirms screen state on a later frame.
29. What was the direct callback-to-close measurement in the broader run? 136-3790 microseconds across 244 samples.
30. Was a production close accelerator added? No; evidence did not justify one.

### Scaling and rendering

31. Can `InventoryScreen` receive both inventory and generic-container transforms? It could; the generic mixin now yields ownership to the inventory-specific path.
32. Can the narrow recipe-book path nest the inventory background scale? It could; active surface ownership now prevents a second push.
33. Are clicks, drags and releases transformed more than once through superclass calls? No after the audit split.
34. Does a scale of exactly 1 still need scope ownership? Yes; `hasActiveSurfaceScope()` tracks ownership independently of numerical scale.
35. Do live customization sliders remain responsive? Yes; rendering invalidates immediately.
36. Does slider dragging write configuration files hundreds of times per gesture? No; persistence is coalesced at release or keyboard adjustment.

## Stress evidence

Offline integrated-server suite with the 26.1.2 debug companion:

- 248 inventory-open attempts, 248 successes, 0 misses.
- 288 assertions, 0 failures.
- 32 held-key close cycles, 32 successes.
- Four bindings remained held in each close cycle: movement, lateral movement, jump and sprint.
- The dedicated held-repeat phase kept the same inventory screen for 12/12
  repeat callbacks in all eight cycles and reported 0 failed assertions.
- No macro abort and no crash.
- Final screen state: none.

The macro is synthetic development instrumentation and is not shipped as gameplay automation. Its result validates the local input path; it does not claim lower server latency or anticheat invisibility.

## Verdict

The reported slow close was not reproduced as a KoHs close-path defect for fresh physical presses. Those presses still close through the native path even with several other keys held. Occasional visual delay can originate before event dispatch when a frame stalls.

The follow-up held-key test uncovered a separate issue that the PRESS/RELEASE tests above did not cover: operating-system REPEAT callbacks can toggle the screen automatically. With Super Fast Inventory enabled, an unshared inventory binding now ignores those repeats in gameplay and the ordinary player inventory. Fresh presses, releases and recipe-search editing retain their normal handling. This deliberately removes hold-generated automatic close messages, so the held sequence is not claimed to be strictly packet-equivalent to Vanilla.

# 26.1.2: one-shot cursor contract

## Scope and pre-change verdict

Center Mouse Fix resolves the enabled custom target (including the existing
item-follow target) or vanilla center during a player-inventory opening. After
the synchronous opening returns, pointer motion must be player-owned. No
container centering, interpolation, input rejection, cooldown or frame retries.

Inspected exact 26.1.2 Loom sources: Minecraft#setScreen, MouseHandler#onMove,
releaseMouse, handleAccumulatedMovement, InputConstants#grabOrReleaseMouse.
Vanilla releases before screen init. The mod finalizes the initialized layout at
setScreen return and clears inherited camera deltas. No later motion hook exists.
Existing dirty fast-open, drag-scale and compatibility edits belong to the user
and are outside this change.

Gap: overrideReleasePosition classifies the current screen even after opening
ends. A later release in an already-open custom inventory can request another
landing. Limit it to the outstanding opening transaction; do not reposition an
unfocused/minimized window. Neither safeguard adds waiting or changes subsequent
mouse input.

### Trust boundary

The transaction/focus guards are local cursor-state gating (L0 in isolation),
with no packet sends or gameplay scheduling. Custom landing as a whole can
change which slot a subsequent real click hits (L2 behavioral effect); this is
not packet equivalence for identical physical input. Existing fast-opening is
not changed or reclassified here. Server-only checks see normal item actions,
not desktop cursor coordinates. Inspecting client files requires client
cooperation. No action retries, cooldown changes, rotation writes or bypasses of
server acknowledgements are added.

## Verification plan

Singleplayer-only debug fixture: assert synchronous physical/internal positions,
free motion immediately and across later polls, and late-release queries.
Cover vanilla/custom/off, fast on/off, GUI 2/3/4, recipe book open/closed and
inherited camera deltas. Synthetic callback tests do not measure hardware
latency or guarantee behavior with arbitrary input mods.

## Changes

- Release-position override now requires the same pending opening screen. No
  custom override can be requested just by releasing again in an open screen.
- Both opening hooks require an active, focused, non-minimized game window.
  This is a guard, not a deferred placement on refocus. Native focus transitions
  are still owned by GLFW/Minecraft.
- The vanilla target uses the exact integer center from 26.1.2 releaseMouse.
  Custom targets resolve to whole window-coordinate pixels so the internal
  position and Windows pointer use one value. In the old baseline, targets such
  as (296.783, 363.335) read back as (296, 363); that could cross the 0.5px
  correction threshold without representing a genuine cursor displacement.
- No change to mouse movement handlers, input queues, fast-open policy, slot
  actions, sensitivity, raw input, keyboard bindings or later-frame behavior.

The [GLFW Win32 implementation](https://github.com/glfw/glfw/blob/master/src/win32_window.c)
converts cursor placement to integer POINT coordinates. Its
[input guide](https://www.glfw.org/docs/latest/input_guide.html#cursor_mode) also
documents that leaving disabled-cursor mode restores the last visible position;
this is why finalizing after release remains necessary. These are native input
semantics, not evidence against any particular third-party mod.

## Executed evidence

Development client only, integrated world `KoHs Debug QA`, with the root 26.1.2
JAR, Fabric API, Mod Menu and debugger 0.2.0. No Modrinth profile was modified.
Both runs closed automatically. No gameplay/item macros or remote-server tests
were executed in this audit.

Logs under `debug/kohs-inventory-debug-26.1.2/run/logs/kohs-inventory-debug/`:

- Baseline `kohs-inventory-debug-20260908-004436.log`: 48 openings, 1,092 checks,
  161 failures. Of these, 120 are deterministic late-release override queries
  (five per custom case), and 41 are native-coordinate mismatches during desktop
  pointer movement. The latter are **not attributed to the mod or claimed fixed**.
  This first run was 854x480: requested 3x/4x could be clamped by vanilla, so it
  does not prove coverage at those effective scales.
- Corrected `kohs-inventory-debug-20260908-004818.log`: **48/48 openings,
  1,092 checks, zero failures**. Window 1440x1000; the log explicitly confirms
  effective GUI scale 2, 3 and 4. Tested book open/closed, fast on/off, vanilla
  target, custom target with center on/off, both features off, scale settings
  65%/200%/315% (subject to screen fit), and 240 large cursor movements followed
  by later-poll checks. Initial native/internal positions are tested before
  render. The same-callback movement assertions require no extra tick or wait.

- Follow-up `kohs-inventory-debug-20260908-005723.log` ran the existing
  `centered-cursor` battery after the fix: **18/18 opens, 0 misses, 18/18
  assertions**, with p50 14,876 microseconds and p95 56,719 microseconds in the
  disposable client. Those timings include development and trace instrumentation;
  they are not a hardware-latency promise. The trace shows no extra landing after
  free movement and no macro abort.

The old generic macro summary counted zero NativeInput-bridge events because this
fixture injects callbacks at the poll hook directly. Its authoritative results
are CURSOR_CONTRACT_SUMMARY, not the generic bridge counter. The companion now
omits that empty generic summary for this lab and labels its bridge count clearly.

Limitations: synthetic callbacks are not an end-to-end mouse latency measurement;
1px tolerance accounts for native coordinates; held-button item dragging,
multiplayer, hardware drivers and additional input mods are not covered by these
48 cases. Focus guards were source-audited, not exercised by stealing OS focus.
No guarantee that arbitrary software cannot move the cursor after the opening is
made; preventing that would require the continuous forcing the user rejected.
